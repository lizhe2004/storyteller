# 单实例运行时配置管理设计

## 1. 背景与目标

当前部署主要依赖 `.env` 和 Docker Compose 配置。使用人员在另一台电脑部署时，需要手工创建和修改环境变量，修改后通常还需要重启容器。本方案为单实例部署增加一个受保护的配置后台，使管理员可以在页面中维护 Web、大模型、TTS、音效等配置。

目标：

- `.env` 仍然可以完成首次启动和基础部署。
- 管理员可以在后台查看、修改和测试运行时配置。
- 配置保存后立即对新任务生效。
- 正在执行的任务继续使用任务启动时的配置快照。
- API Key 等敏感值不回显、不写入普通业务日志、不进入镜像。
- 容器重启后后台配置仍然保留。

非目标：

- 不做多租户配置隔离。
- 不做复杂的角色权限系统。
- 不自动修改宿主机 `.env` 或 Docker Compose 文件。
- 不自动更新 `voices.json` 等业务数据。

## 2. 配置来源与优先级

配置来源按以下顺序生效：

```text
后台已保存配置 > 环境变量 > 程序默认值
```

环境变量仍由现有 `.env` 和容器环境提供。后台覆盖配置保存于数据目录，例如：

```text
/data/config/settings.json
```

首次启动时，如果后台没有保存覆盖项，系统直接使用现有环境变量。删除某项后台覆盖后，该项回退到环境变量或程序默认值。

配置读取应通过统一的运行时配置服务完成，业务代码不再在任务执行过程中零散读取环境变量。每个新任务开始时获取一次不可变配置快照并传给任务上下文；任务执行期间不重新读取全局配置。

## 3. 配置范围

### Web 服务配置

- `STORYTELLER_WEB_PASSWORDS`
- `STORYTELLER_WEB_SECRET`
- `STORYTELLER_WEB_CONCURRENCY`
- `STORYTELLER_WEB_TOKEN_TTL_DAYS`
- `STORYTELLER_WEB_RATE_LIMIT_PER_MIN`
- `STORYTELLER_LOG_LEVEL`

监听地址、容器端口和数据目录由 Docker/部署配置控制，后台只读展示，不允许在线修改，避免修改后与容器端口映射或挂载路径不一致。

### LLM Provider 配置

每个 Provider 支持：

- 启用状态
- API Key
- 模型名
- Endpoint
- Provider 顺序
- 默认 Provider

第一期覆盖现有 Volcengine、Gemini 和 OpenAI-compatible 配置结构，并保留 Provider 专属字段的扩展入口。

### TTS Provider 配置

每个 Provider 支持：

- 启用状态
- API Key
- 模型名
- Endpoint
- 资源 ID、Workspace 等 Provider 专属字段
- Provider 顺序
- 默认 Provider

### 音效配置

- 音效能力开关
- 音效 Provider
- 音效模型
- 音效 Endpoint
- 音效 API Key

## 4. 敏感信息处理

API Key、Web Secret 和访问密码属于敏感配置。

- GET 配置接口只返回是否已配置、脱敏尾部或占位符，不返回完整值。
- 更新时支持替换和清空；提交空值不应意外覆盖已有密钥，清空必须由明确操作表达。
- 服务器日志不得记录完整请求体、完整配置或 API Key。
- 配置文件写入权限为 `600`，父目录权限至少限制为应用用户可访问。
- 文件写入采用临时文件、刷新、替换的原子流程，避免容器异常退出留下半份 JSON。
- 配置备份和错误日志不得包含明文密钥。

第一期可以使用数据卷内受限权限的配置文件保存密钥，不把密钥放入镜像或前端存储。后续如有更高安全要求，再接入 Docker secrets 或外部 Secret Manager。

## 5. 后端接口

建议新增受保护的配置接口：

- `GET /api/settings`：返回分组配置、当前生效来源和脱敏状态。
- `PATCH /api/settings`：部分更新配置，校验字段类型、Provider、Endpoint 和必填关系。
- `POST /api/settings/test/llm`：使用提交的临时配置测试 LLM 连接，不保存测试参数。
- `POST /api/settings/test/tts`：使用提交的临时配置测试 TTS 连接，不保存测试参数。
- `POST /api/settings/reset`：删除指定覆盖项，回退到环境变量。
- `GET /api/settings/history`：返回不包含敏感值的修改记录，第一期可只保留最近若干条。

保存接口返回配置版本号和生效时间。测试接口需要设置超时，并将供应商错误转换为不泄露密钥的用户可读信息。

## 6. 前端页面

新增“系统配置”页面，按以下区块组织：

- Web 服务
- 大模型
- TTS 音色服务
- 音效与高级设置

每项展示：当前值、配置来源、是否已配置和最后修改时间。敏感字段使用密码输入框，默认显示脱敏状态。

交互包括：

- 保存当前分组
- 测试连接
- 恢复为环境变量值
- 恢复全部默认配置
- 未保存修改离开页面时提示
- 保存成功后提示“已对新任务生效”

监听地址、端口和数据目录以只读方式展示，并说明需要通过 Docker Compose 修改。

## 7. 生效与错误处理

配置保存时进行结构校验，但不要求所有 Provider 都已配置，因为系统允许 Provider 组合和按需启用。

新任务启动时：

1. 读取当前配置快照。
2. 校验任务所需 Provider 是否可用。
3. 将快照绑定到任务上下文。
4. 后续调用只使用该快照。

保存失败时不修改内存配置。配置文件损坏时，服务启动应记录明确错误并回退到环境变量，同时禁止静默使用不完整配置；后台需要显示配置文件异常状态。

## 8. Docker 部署方式

Compose 使用 Docker Hub 镜像时，`docker-compose.yml` 保留 `env_file: .env`，并将镜像指向：

```yaml
image: lizhe2004/audio-story-generator:latest
```

配置覆盖文件位于数据卷 `/data/config/settings.json`，因此用户更新镜像或重建容器时不会丢失后台配置。使用人员只需准备 Compose 文件和 `.env.example`，首次部署时创建 `.env` 并填写密钥。

## 9. 测试范围

- 配置来源优先级测试：后台覆盖、环境变量、默认值。
- 敏感字段脱敏和不可回读测试。
- 配置原子写入、损坏文件回退和权限测试。
- 新任务获取配置快照，运行中配置变更不影响旧任务。
- Provider 测试接口成功、超时和错误响应测试。
- 配置 API 的认证测试。
- 前端分组编辑、保存、测试连接、回退和未保存提示测试。
- Docker Compose 使用 `.env` 和 `/data` 数据卷的部署验证。
